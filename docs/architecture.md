# Architecture — detail

Read this when a task requires touching `webapp/` structure, Supabase
client selection, i18n, or env vars. See `CLAUDE.md` for the one-line
version of most of this.

## Repo layout

```
osem-webapp/
├── webapp/               Next.js app — this is what staff actually use
├── migration/            One-off Python scripts that move data Access → Supabase
├── schema/                Hand-written Postgres schema (schema/001_init.sql)
├── google-apps-script/   Code deployed to Google Apps Script (Drive integration)
└── docs/                 This directory — detailed reference docs
```

## `webapp/` internals

- Next.js 16 (App Router), React 19, Tailwind v4, TypeScript.
- `src/app/(app)/` — one folder per top-level nav tab: `residents/`,
  `clinical/`, `physiotherapy/`, `staff/`, `accounts/`.
- `src/app/(app)/clinical/` has its own sub-tabs, each a `*-module.tsx` +
  `*-actions.ts` (Server Actions) pair: Nursing Chart, Vital Signs, Wound
  Photo, Medical Progress Notes, Hospital Referral.
- `src/lib/supabase/{client,server,admin}.ts` — Supabase client factories.
  `server.ts` is what Server Components/Actions use (respects RLS via the
  signed-in session); `admin.ts` uses the service-role key for the rare
  admin-only action (e.g. inviting a staff login).
- `src/lib/i18n/` — English/Bahasa Malaysia switcher, split into
  `dict-*.ts` files by module plus `translations.ts` (aggregates them into
  `msDictionary`) and `translate.ts` (the `t()` helper). `t("English text")`
  looks the string up; a missing key just falls back to English — not a
  build error. New UI text doesn't need a translation to compile, but
  should get one in the relevant `dict-*.ts`.
- Env vars: see `webapp/.env.local.example`. Supabase URL/anon key are
  public; `SUPABASE_SERVICE_ROLE_KEY`, `GOOGLE_APPS_SCRIPT_*`, and
  `OMNIROUTE_*` are server-only, never `NEXT_PUBLIC_`.
- Run locally: `cd webapp && npm run dev` (or `preview_start` with the
  `.claude/launch.json` config `osem-webapp-dev` if the Browser pane is
  available).

## `migration/`

One-off Python scripts (`migration/scripts/*.py`) that read the Access
`.accdb` (via `access_reader.py`) and write into Supabase (via `PG_DSN` in
`migration/.env` — direct Postgres connection, not the REST API). Each
script is single-purpose and named for what it does
(`add_wound_photo_tables.py`, `rework_wound_body_parts.py`,
`create_physio_assessment_tables.py`, `reset_osemnursing_test_pw.py`,
etc.) — no migration framework/runner beyond `run_migration.py` for the
original Access→Supabase ETL pass. **Running one of these touches the
real Supabase database** — confirm with the user first unless it's
clearly read-only.

## `schema/001_init.sql`

The hand-written source-of-truth schema (enums, tables, RLS policies) as
it looked at initial rollout, plus later numbered migration files (e.g.
`002_add_bed_capacity.sql`) for specific additive changes. **Not** kept in
sync with every `alter table` run ad hoc through a migration script or the
Supabase SQL editor — treat `001_init.sql` as a snapshot of original
design intent and enum values, and check the live database (or the
relevant `migration/scripts/*.py`) for current truth on anything that
might have changed since. RLS helper functions (`auth_role()`,
`auth_branch_id()`, `auth_account_id()`) live near the bottom of
`001_init.sql` (moved there after an ordering bug where earlier policies
referenced them before they were defined).

## Other repo-root Markdown files

`COMPLETION_SUMMARY.md`, `IMPLEMENTATION_SUMMARY.md`, and
`DEPLOYMENT_INSTRUCTIONS.md` are historical, single-feature snapshots (the
Admission Analytics / bed-capacity drill-down work) written mid-project —
not standing rules, and superseded by the shipped code + git history. Do
not treat them as authoritative; `docs/deployment.md` is the canonical,
current deployment reference. `webapp/AGENTS.md` / `webapp/CLAUDE.md` are
Next.js's own auto-generated dev-server notice (regenerated by
`next dev`), not project documentation.
