# i18n architecture (English / Bahasa Malaysia)

Full reference for the translation system CLAUDE.md's i18n rule points to.
Current languages: `en` (default) and `ms`. Adding a third language later
means adding a third `Language` union member and one more merged dict file
— no per-module redesign, because of the dictionary-key convention below.

## How it works

- **The dictionary key is the literal English string**, not a generated
  code — `src/lib/i18n/translate.ts`'s `translate(text, language, params?)`
  looks `text` up in `msDictionary` (only when `language === "ms"`) and
  falls back to `text` itself on a miss. A missing MS entry is silently
  safe (English shows), never a broken key or a crash.
- **Client components**: `useTranslation()` (`src/components/language-provider.tsx`)
  returns `t(text, params?)`. `useLanguage()` also gives `{ language, setLanguage }`
  for the switcher itself.
- **Server Components**: `getServerTranslator()` (`src/lib/i18n/server.ts`)
  reads the `osem_lang` cookie and returns `{ language, t }`.
- **Interpolation**: `t("Showing {count} residents", { count })` — the
  English key keeps its `{placeholder}` tokens; the MS translation can
  reorder them freely (grammar differs) without touching the call site.
  `TranslateParams = Record<string, string | number>`.
- **Dictionaries are owned per module**: `src/lib/i18n/dict-<module>.ts`,
  merged into one flat `msDictionary` by `translations.ts`. Add a new
  `dict-<module>.ts` for a new module rather than growing an existing file
  or inlining translations elsewhere — `npm run check:i18n` (see below)
  catches the one real hazard this creates: two dict files defining the
  same English key with different Malay text (last file spread in
  `translations.ts` wins silently).

## The dropdown/option rule (read this before adding any `<select>`)

**Never hardcode a displayed option label.** The stored value and the
displayed label are two different things that happen to often be the same
string in English:

```tsx
// Correct: value is stable, label is translated. The DB never sees "ms".
{MOBILITY_OPTIONS.map((o) => (
  <option key={o} value={o}>{t(o)}</option>
))}

// Correct: explicit {value, label} shape when the stored value and the
// natural display text genuinely differ (e.g. an id + a name).
{options.map((opt) => (
  <option key={opt.value} value={opt.value}>{t(opt.label)}</option>
))}

// Wrong: value is never translated for storage, but label is never
// translated for display either -- an untranslated dropdown.
{STAFF_ROLE_OPTIONS.map((r) => <option value={r}>{r}</option>)}
```

This applies identically to a custom dropdown, a filter menu, a status
badge, a chart legend, or a table cell showing a stored enum value — any
place a fixed-vocabulary value is displayed to a user. **Never translate
the stored value itself** (`ACTIVE` must stay `ACTIVE` in the database
forever, even though the UI shows "Aktif"); only the label passed to `t()`
changes with the language.

### DB-driven lookup tables are a known exception, not a bug

A large share of this app's dropdowns (`tbl_bowel_output_types`,
`tbl_positions`, `tbl_wound_body_parts`, `tbl_physio_treatment_types`,
branches, staff names, nationalities, and everything else fetched through
`lib/lookups.ts`) get their **label text from a Supabase row**, not from a
literal in the TypeScript source. `t()` cannot translate a runtime string
it has never seen at build time — there is no dictionary key to look up.

One table already solves this correctly: `tbl_diagnosis_options` has both
`name_en` and `name_ms` columns, and `getDiagnosisOptions()` returns both
so the caller picks by language. **This is the pattern for any lookup
table that genuinely needs Bahasa Malaysia labels** — add a `_ms` column,
not a code-side translation layer. It is a schema change, so it wasn't
done for the ~15 other lookup tables in this pass (see Limitations below);
treat it as the standard next step when one of them needs MS coverage.

Proper nouns from these tables (branch names, staff names, nationalities)
are correctly never translated at all — that's not a gap.

## Adding a new module

1. Create `src/lib/i18n/dict-<module>.ts` exporting `dict<Module>: Record<string, string>`.
2. Add it to the merge list in `src/lib/i18n/translations.ts`.
3. Every string a user sees — labels, buttons, placeholders, empty states,
   error messages, dropdown option labels — goes through `t()`. Never a bare
   JSX text node or a hardcoded `<option>` body.
4. Run `npm run check:i18n` before opening a PR (see below) and add any
   flagged missing keys to your module's dict file.
5. If a value is dynamic (a count, a name), use `t("... {x} ...", { x })`
   — never build the sentence by concatenating separately-translated
   fragments (`t("Select") + " " + t("resident")`); word order differs
   between languages and that pattern can't be reviewed as one sentence.

## The completeness check (`npm run check:i18n`)

`scripts/check-i18n.mjs` is a plain static text scan — not a TypeScript/JSX
parser — run with `node scripts/check-i18n.mjs` (or `npm run check:i18n`).
It checks three things:

1. **Duplicate dictionary keys** — the same English key defined with a
   different Malay value in two `dict-*.ts` files. This is the one thing
   it treats as an **error** (non-zero exit), because it's silently wrong
   today, not just incomplete.
2. **Missing translations** — every `t("literal")` call site in `src/`
   whose key has no entry in any `dict-*.ts` file. Informational only —
   the app still renders in English for that string — but should trend
   toward zero.
3. **Untranslated `<option>` labels** — a heuristic scan for `<option>`
   tags whose visible text is a literal string rather than a `t(...)`
   call.

### Limitations of the automated check (read before trusting or dismissing its output)

- It only sees `t("literal string")` calls with the key written directly
  as a string literal. `t(someVariable)` or `t(\`${x}\`)` is invisible to
  it — don't rely on it to catch a dynamic-key mistake.
- The `<option>` heuristic matches by tag text, not by data flow. A DB-driven
  proper noun (branch/staff name) will show up as a false positive; a
  translated label built from a helper function three files away that
  happens to return raw English will be missed entirely. Read the flagged
  line before acting on it either way.
- It cannot see hardcoded strings in Server Actions' returned `{ error }`
  messages, PDF report templates, or anywhere else a string is built and
  handed to a component rather than passed through `t()` directly at the
  render site — see "Known gaps" below for why those need a different fix,
  not a smarter regex.
- It does not attempt real JSX parsing (no acorn/babel/typescript AST), so
  a raw English sentence sitting directly as JSX children (`<p>Some text</p>`)
  is not flagged at all. This is a real, intentional limitation: reliably
  telling "English UI copy" apart from "a technical term/class name/short
  variable" in arbitrary JSX text nodes needs true parsing, and the false
  positive rate of a regex attempt at that was judged not worth it. New
  code review is still the primary defense against this category.

## Known gaps (as of this audit — not fixed in this pass)

These are architecture-level, not a missed `t()` call, and each needs more
than a one-line fix:

- **Server Actions never translate their own error messages.** Every
  `"use server"` action file (`residents/actions.ts`, `accounts/actions.ts`,
  `staff/actions.ts`, every `clinical/*-actions.ts`, `physiotherapy/actions.ts`,
  `order-actions.ts`, ~14 files total) returns `{ error: "hardcoded English" }`
  directly, with no `getServerTranslator()` call. The client side then
  renders that string as-is. Fixing this properly means giving every
  Server Action the same `t` a Server Component gets, and re-keying each
  returned message through it — a real but mechanical refactor across all
  14 files, not attempted in this pass.
- **PDF/report generation cannot render in Bahasa Malaysia at all.** None
  of the 7 routes under `app/api/reports/**`, nor any of the `lib/pdf/documents/*.tsx`
  templates, read the language cookie or call `t()` — every label is a
  hardcoded English string literal. Fixing this needs the report route to
  read `getServerLanguage()` and thread a translator into each PDF
  document component.
- **Supabase Auth SDK error messages** (`error.message` from `signInWithPassword`,
  `resetPasswordForEmail`, `updateUser`) are English strings from the SDK
  itself, not app code — `t()` can't translate them without a lookup table
  keyed on Supabase's own error codes/messages.
- **Physiotherapy score dropdowns** (`lib/physio-scoring.ts`'s `ScoreOption`
  arrays for Power/Tone/ROM/Reflexes/Balance/Coordination/Functional) build
  `label` as a compound string (`` `${value} — ${description}` ``) at
  module load time, so there is no clean dictionary key to translate — the
  number and the English description are baked into one string. Needs
  `ScoreOption` to carry `value`/`description` separately before this can
  be translated at all.
- **Free-text summaries compiled from form answers** (resident admission's
  arrival questionnaire, hospital referral's vital-signs summary, nursing
  chart's hygiene/meal "assistance level: activities" composites) are
  built server- or client-side into one English sentence and stored, then
  displayed verbatim later. These can never be localized after the fact
  without re-parsing stored text — the fix is to store structured data and
  compose the sentence at render time through `t()`, not at write time.
- **DB-driven lookup tables without a `_ms` column** (everything in
  `lib/lookups.ts` except `tbl_diagnosis_options`) — see "DB-driven lookup
  tables" above.
- **26 duplicate dictionary keys with identical values** across module
  dict files (e.g. `"Branch"` defined in four files) — harmless today (same
  Malay text each time) but redundant; worth consolidating into
  `dict-common.ts` opportunistically, flagged by `npm run check:i18n` for
  whoever picks that up.
